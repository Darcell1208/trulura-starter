# ADR-003: Navigation Shell

**Status:** Proposed / undecided — this ADR names no recommended direction

## Context

26 of ~30 screens currently rebuild their own `Scaffold` independently rather than using `MainShell`'s persistent chrome (Technical Debt TD-08). Separately, and at a different layer, the Blueprint itself contains an internal contradiction: **PD-14** — "Which Primary Navigation structure is correct — Section 10.9.1 (Aura/Sync/Explore, 3 tabs) or Section 20.2.1 (Feed-Discovery/Messaging/Profile/Mode Switching, 4 items)?" (`docs/02-Product/TruLura_Product-Decisions.md.md`). PD-14 is Critical and blocks both Section 10 and Section 20 outright (Beta Readiness Checklist). The current Flutter implementation is a hybrid of both candidates, built independently of this conflict being known: `MainShell` has 4 branches (Home/Messages/Notifications/Profile, closer to 20.2.1's cardinality), but Home internally tab-switches between exactly Aura/Sync/Explore — 10.9.1's three items verbatim, one level deeper than the Blueprint specifies (`TruLura_Blueprint-to-Code-Matrix.md` §02).

## Decision

**Not yet decided.** This ADR's own question — how far persistent chrome should extend beyond the current 4 tabs — is downstream of PD-14, not equivalent to it, and cannot be answered until PD-14 resolves.

## Alternatives Considered

- Leave chrome as-is, formally documenting which routes are intentionally "modal" (settings, vent, matchroom) vs. accidentally inconsistent.
- Extend `MainShell` to wrap every route — likely unnecessary for genuinely modal flows.
- Standardize the already-existing, underused `TruluraScreenShell` widget as shared app-bar/back-button chrome for non-tab routes, without nesting them inside the bottom-nav shell.

## Reasoning

Flagged as undecided rather than guessed, per the standing rule to ground findings in evidence, not speculation, and per the Documentation Constitution's rule that product decisions are never authored by engineering.

## Consequences

Gates ENG-012 (persistent chrome extent) directly, and ADR-001/ENG-004 (Unified Session Object) indirectly, per standing instruction that the navigation decision must resolve first.

## Migration Strategy — Incremental Migration Rule

**Can this be implemented incrementally?** Not yet answerable — no direction has been chosen. Whichever way PD-14 resolves, the cost is asymmetric: confirming the Blueprint's 10.9.1 structure costs little (code already matches it, tabs would just need promoting one level up if a literal 3-tab bottom nav is wanted); confirming 20.2.1 costs more (a "Mode Switching" primary nav item doesn't exist in code today).
