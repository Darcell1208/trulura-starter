# ADR-004: State Management Approach

**Status:** Proposed — not approved, not started

## Context

`main.dart` wraps the app in a real, working Riverpod `ProviderScope` (`flutter_riverpod: ^3.3.1` is a genuine dependency), but zero Riverpod providers or consumers exist anywhere else in `lib/` (Technical Debt TD-14). The app's real state mechanism is `lib/compat/provider_compat.dart`, a hand-rolled `InheritedNotifier`-based replacement for the `provider` pub package, used in 57+ files and working correctly.

## Decision

Keep `provider_compat.dart` as the state-management mechanism; remove the unused Riverpod dependency as separate cleanup (TD-14); build ADR-001's composed session object on the existing mechanism, not on Riverpod.

## Alternatives Considered

- Fully adopt Riverpod now, migrating the composed session object (ADR-001) directly onto it — compounds two large changes (new topology + new library) at once.
- Adopt Bloc/Cubit — a larger library switch with no evidence it solves a problem `provider_compat.dart` doesn't already solve; rejected under the Incremental Migration Rule.
- **Keep `provider_compat.dart`, remove Riverpod separately.**

## Reasoning

`provider_compat.dart` already works and is in wide use; switching the underlying library at the same moment as restructuring the provider topology would violate the Incremental Migration Rule by compounding two large changes into one.

## Consequences

Riverpod dependency removed (TD-14, ENG-014). If a future, specific need for Riverpod (codegen, testing ergonomics) emerges, that becomes its own separate ADR rather than being bundled here.

## Migration Strategy — Incremental Migration Rule

**Can this be implemented incrementally? Yes.** Delete the `ProviderScope` wrapper and the dependency; confirm via `flutter analyze` that nothing depended on it (nothing should, per the evidence above).
