# ADR-001: Unified Session Object

**Status:** Proposed — not approved, not started

## Context

Identity is fragmented across four independent stores (`AppProvider`, `UserService`, `IdentityService`, `IdentityProfileService`) and only 4 of many write paths keep them synchronized (Architecture Map, Emotional Core Audit; Technical Debt TD-01, TD-13). This directly violates the Product Constitution's "Identity Is Singular and Contextual, Not Fragmented" principle, itself grounded in Blueprint §1.1: "Each user has one master identity." Separately, mood/emotional state exists twice (`emotionalPresenceState` vs. `AuraController.state`) with no sync between them (TD-02), violating Guiding Principle 5 ("MoodSync is the one emotional source of truth"). Both are symptoms of the same missing piece: no composition root exists for cross-cutting user state. Independently, the Product Knowledge System's own Engineering Gap Register names the same underlying problem from the product side as **EG-01, Permission Resolution** — "no formula for combining Mode + Trust Score + Verification Level + Emotional State into one access decision," the single most-referenced gap in the Blueprint.

## Decision

Replace the five independent sibling `ChangeNotifier` providers with one composed session object that owns identity, emotional, profile, companion, and sync sub-state.

## Alternatives Considered

- Keep the five siblings, patch every write path to refresh `AppProvider` — treats the symptom, not the topology; new features would keep reproducing the same fragmentation.
- Fully adopt Riverpod (the dormant dependency already in `pubspec.yaml`) as the new state layer — a second large, non-incremental change happening at the same time as a structural rewrite; rejected (see ADR-004, and the Incremental Migration Rule).
- **One composed session object, introduced incrementally** — matches the one composition pattern already in the codebase (`ExperienceModeController` already takes `AppProvider` as a constructor dependency), the smallest structural change that addresses the root cause.

## Reasoning

Fixes the structural cause rather than each symptom individually; builds on an existing, proven composition pattern in the codebase rather than introducing a new one; directly implements what the Blueprint's own gap register (EG-01) independently identifies as the most-referenced open gap in the entire product.

## Consequences

Every screen currently reading 2+ providers eventually migrates its reads. The 5 existing providers are retired only once nothing references them. Unlocks consistent identity/mood/companion/sync state as a direct side effect. Resolves the two Constitution-level violations named in `TruLura_Repository-Architecture.md`.

## Migration Strategy — Incremental Migration Rule

**Can this be implemented incrementally? Yes.** Introduce the new store behind the existing `AppProvider` API first (no call-site changes), then migrate write paths one screen at a time, verified against the existing screen list. Old providers are removed last, only once nothing references them.

**Explicitly not started.** Waiting on: PD-14 (navigation, see ADR-003) resolving, and Feature-to-Code Matrix confirmation of scope, per standing instruction.
