# ADR-005: Backend Strategy

**Status:** Proposed — sequencing pending the Blueprint's own priority confirmation

## Context

Chat, Sync/Matchmaking, Notifications, Companion, and Creator Platform all currently lack real backend support despite reading as backend-driven features (`TruLura_Backend-Readiness.md`, `docs/04-Engineering`). Only 6 Supabase tables are in use, touched by 4 files, with zero `.rpc()` calls and no realtime channel subscriptions anywhere in `lib/`.

## Decision

Continue building on Supabase (the established backend); sequence the missing pieces by Beta priority as confirmed in the Product Knowledge System (`docs/02-Product/TruLura_Beta-Readiness-Checklist.md.md`), not by engineering convenience. Chat/Sync is treated as Critical now because Sync/Spark (base) is confirmed Core Beta; Chat itself has no clear matching Blueprint section (see `TruLura_Engineering-Governance.md` §02, EQ-01).

## Alternatives Considered

- Build every missing backend before Beta — thorough but not evidence-justified until each area's actual Beta requirement is confirmed.
- Adopt a separate third-party service for real-time chat specifically — a new dependency; Supabase already supports realtime channels (currently unused in `lib/`), so this isn't yet justified by anything in the repository or the Blueprint.
- **Continue on Supabase, sequence by confirmed Beta priority.**

## Reasoning

No evidence yet justifies introducing a second backend platform; Supabase already covers everything currently needed, including realtime capability not yet exercised.

## Consequences

ENG-002, ENG-006, ENG-013 all build on this direction; their relative order is set by Beta Readiness confirmation, not by this ADR.

## Migration Strategy — Incremental Migration Rule

**Can this be implemented incrementally? Yes**, per feature area: schema design first (needs Product input on match/message semantics for Sync/Chat — see PD-06, EQ-01), then a repository swap behind existing service interfaces so screens don't need to change.
