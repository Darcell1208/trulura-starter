# ADR-002: Repository Pattern

**Status:** Proposed — not approved, not started

## Context

No class or file matching `*Repository*` exists anywhere in `lib/` (Architecture Map §08; Technical Debt TD-04). Services mix business logic and raw Supabase query construction in the same methods — e.g. `UserService` and `PostService` build `.from(table)` queries inline next to domain normalization logic, and `AppProvider` embeds a ~150-line hand-written row-to-`User` mapper directly inside a `ChangeNotifier`.

## Decision

Introduce a thin repository interface per model (e.g. `UserRepository`, `PostRepository`) that owns query construction; services call the interface and keep only business logic.

## Alternatives Considered

- Leave as-is — the inconsistency compounds every time a new backend model is added (Chat, Sync, Notifications, Creator Platform are all pending, per `TruLura_Repository-Impact.md`).
- Adopt a full ORM/codegen layer — likely disproportionate for the 6 tables currently in use; no evidence yet justifies the added dependency.
- **Thin, manually-written repository interfaces per model** — minimal surface change, no new dependency.

## Reasoning

Smallest change that separates "what data looks like" from "how it's fetched," which is the actual gap; fits the team's current patterns without new tooling.

## Consequences

Services become thinner. Every new backend model (Chat/Message, Match, Notification, Creator profile) lands on the improved pattern from day one instead of extending the inconsistent one.

## Migration Strategy — Incremental Migration Rule

**Can this be implemented incrementally? Yes.** One repository per existing table (`profiles`, `matchmaking_profiles`, `user_states`, `posts`, `post_reactions`, `user_settings`), services swapped in individually, no behavior change per step. The pattern extends to any new backend model going forward rather than requiring a retrofit of everything at once.
